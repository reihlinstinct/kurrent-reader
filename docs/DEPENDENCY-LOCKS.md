# Dependency locks (#63)

Every documented install reads a lock under `requirements/`, so a changed or
substituted package fails the install instead of running. The pattern
follows parking-report-helper #177 and parking-category-model #40, scaled to
this repo, plus the PyTorch CPU index.

## The locks

| Lock | Generated from | Covers |
|---|---|---|
| `requirements/build.txt` | `requirements/build.in` (= `[build-system] requires`) | setuptools, for `--no-build-isolation` |
| `requirements/core.txt` | `pyproject.toml` `dependencies` + `requirements/torch.in` | runtime, CPU torch included |
| `requirements/dev.txt` | the same + the `dev` extra, constrained by `core.txt` | runtime + pytest, mypy |

Every line is an exact `==` pin with sha256 hashes, generated by
`uv pip compile --universal --generate-hashes --python-version 3.11`. The
specs in `pyproject.toml` are unchanged and are the only inputs besides
`requirements/torch.in`, which holds the torch range CI and the Dockerfile
used before (`torch>=2.9,<=2.14`, kraken's own range). Each lock pins the
newest versions inside those specs (for example kraken 7.1.1,
transformers 4.57.6, safetensors 0.7.0, click 8.2.1, numpy 2.4.6,
torch 2.14.0+cpu, pytest 9.2.0, mypy 2.4.1). The `pytest` that the CI
workflows add next to `.[dev]` is already in the `dev` extra.

`requirements/lock-evidence.json` records, per lock, the generating
command, a digest of its inputs (the `pyproject.toml` sections, `.in` file
and constraint lock it reads) and a digest of the lock itself.

## CPU torch: where it comes from

`torch` and `torchvision` are locked from the PyTorch CPU index
(https://download.pytorch.org/whl/cpu) through uv's `--torch-backend cpu`
option, given on the command line; `pyproject.toml` has no `[tool.uv]`
index or source table. Every other package comes from PyPI. The locks carry:

- `torch==2.14.0+cpu ; sys_platform != 'darwin'` and
  `torchvision==0.29.2+cpu ; sys_platform != 'darwin'` (the CPU builds);
- `torch==2.14.0 ; sys_platform == 'darwin'` and
  `torchvision==0.29.2 ; sys_platform == 'darwin'` (the CPU index's macOS
  wheels carry no `+cpu` label);
- no `nvidia-*` or `triton` packages.

`torchvision` comes from the CPU index too, not only `torch`. On a CPU
build of torch, the PyPI `torchvision` 0.29.2 wheel fails at import
(`RuntimeError: operator torchvision::nms does not exist`), and with it
`import kraken.blla`; the CPU build `0.29.2+cpu` imports and runs. The
other ways to point uv at the CPU index for torch alone do not give a
hashed lock: `--find-links` writes no hashes for those files, a
`[sources]` table is refused outside `pyproject.toml`, and `--index` either
fails (first-index: torchmetrics is on the CPU index at an older version
only) or takes numpy, pillow and others from the CPU index as well
(unsafe-best-match).

The install adds the CPU index with
`--extra-index-url https://download.pytorch.org/whl/cpu`. The hashes decide
which files are accepted, so the extra index cannot substitute a package.

## Python versions and platforms

- **Python 3.11 to 3.13** install from these locks. The CI and Docker
  target, Linux x86_64, has a wheel for every pin.
- **Python 3.14 and newer cannot install yet**: every kraken release
  requires Python `<3.14` (kraken 7.1.1: `Requires-Python <3.14,>=3.10`), so
  pip stops at kraken (#39). The locks are not changed to work around this;
  re-lock once kraken publishes a release for 3.14.
- **macOS arm64** (macOS 14 or newer): every pin has a wheel.
- **Linux aarch64 and Windows x86_64**: every pin has a wheel except
  coremltools 9.0 (a kraken dependency), which ships macOS and Linux x86_64
  wheels only, so pip has to build it from its hashed source archive there
  (not tried here).
- **macOS x86_64**: no torch release in kraken's range (2.9 to 2.14) has an
  Intel Mac wheel, on PyPI or the CPU index, so it cannot install, as before
  these locks.

## Install

```bash
pip install --require-hashes -r requirements/build.txt
pip install --require-hashes --extra-index-url https://download.pytorch.org/whl/cpu -r requirements/dev.txt
pip install --no-deps --no-build-isolation -e ./
```

Use `requirements/core.txt` instead of `dev.txt`, and `./` instead of
`-e ./`, for a runtime-only install. The project installs with no
dependency selection and no build isolation, after the pinned build
prerequisites, so every package on the machine came from a lock. The
Dockerfile runs the same steps (core first, then the dev lock with
`--no-deps`).

## Re-locking

After changing a spec in `pyproject.toml` (or `[build-system] requires`,
and then `requirements/build.in` to match, or the torch range in
`requirements/torch.in`), regenerate every lock with the command in its
header, from the repository root, then re-record the evidence:

```bash
uv pip compile --universal --generate-hashes --python-version 3.11 requirements/build.in -o requirements/build.txt
uv pip compile --universal --generate-hashes --python-version 3.11 --torch-backend cpu pyproject.toml requirements/torch.in -o requirements/core.txt
uv pip compile --universal --generate-hashes --python-version 3.11 --torch-backend cpu pyproject.toml requirements/torch.in --extra dev -c requirements/core.txt -o requirements/dev.txt
python scripts/check_install_pins.py --write-evidence
python scripts/check_install_pins.py
```

Add the --upgrade option to the compile commands to move to newer releases
on purpose. Commit the locks and the evidence file together.

## The guard

`scripts/check_install_pins.py` (standard library only, offline; tests in
`tests/test_install_pins.py`, which also run it on the repository) fails on:

- an install command in tracked Markdown (fenced code and inline code), a
  Dockerfile `RUN` or a workflow `run:` step that installs by name, by URL,
  unpinned, from a file that is not one of the locks, from a lock without
  --require-hashes, or the local project without --no-deps
  --no-build-isolation; pip, `python -m pip` with global options, pip3.X,
  `uv pip`, `uv tool`, pipx and easy_install are all recognised, as is an
  installer behind a variable;
- any index option (`--index-url`, `-i`, `--find-links`, `--index`, ...)
  other than `--extra-index-url https://download.pytorch.org/whl/cpu` on a
  hashed lock install;
- a lock line that is not an exact `==` pin or has no sha256 hash, a header
  that does not show the generating command, a top-level requirement outside
  its `pyproject.toml` or `torch.in` spec, a pin that disagrees with another
  lock, a torch or torchvision pin off macOS without `+cpu`, a CUDA package,
  `requirements/build.in` drifting from `[build-system] requires`, and a lock
  or input that changed without new evidence.

## Workflows

The workflows under `.github/` are changed by the maintainer, not in
contributor PRs. Until the hashed install lands there,
`requirements/pending-workflow-installs.json` names the remaining install
lines (`tests.yml` 32 and 33, `tests-next.yml` 31 and 32, `release.yml` 19)
by path, line and command. The guard reports them as pending instead of
failing, fails when an entry stops matching a violating line, and accepts
only `.github/workflows/` paths. The workflow change deletes the file in the
same commit, and drops the matching `unhashed-pip-install` entries from
`.github/scorecard-baseline.json`, which the offline Scorecard guard would
otherwise report as stale.
